# Campus Manager review — September 28, 2026

The highest priorities are authorization, the frontend cache, import integrity, and release isolation. Several findings affect the behavior promised in the README, rather than being stylistic improvements.

This review covers the current working tree, including the existing beta image-import changes and regression test. Those changes were preserved. Reviewed areas include plugin initialization, roles and manager screens, REST endpoints, import/export, recurrence storage, calendar components and hooks, blocks, updater, dependencies, and packaging. Findings below are based on source tracing unless explicitly marked as reproduced. They are not a claim that a live site has been compromised.

## Validation performed

- **Reproduced:** the actual TypeScript API service returned the organization-10 response for organization 20 and page two, with only one network request. Node's TypeScript support and a mocked `fetch` were used; no live site was contacted.
- **Passed:** clean dependency installation with npm 10, followed by both `build:wordpress` and `build:widget`, in an isolated temporary copy. The default npm on this machine rejected the lockfile with `Missing: react@0.0.0 from lock file`; npm 10 succeeded. Pinning the supported toolchain would remove this ambiguity.
- **Failed:** `npm run lint` because no ESLint configuration exists. The script also excludes `.ts` and `.tsx`, where most frontend logic lives.
- **Dependency audit:** `npm audit --omit=dev` reported six affected dependency entries: five high and one moderate. This is package metadata, not six independently exploitable production vulnerabilities. Exposure must be checked against actual imports and execution paths.
- **Passed:** `git diff --check` for the pre-existing changes.
- **Not run:** PHP lint, the existing 11-case PHP media regression suite, WordPress integration tests, or a live browser/accessibility walkthrough. PHP and DDEV were unavailable in this shell, and the installed Docker client had no running daemon. Prior verification recorded in the README was not treated as a test performed during this review.
- Builds and dependency installation happened outside the repository. No application code was changed by this review.

## Fix first

### 1. P1 — Import authorization permits publishing and overwriting events without event permissions

Evidence: [import permission](/Users/ahmadjalil/github/campusmanager/includes/class-event-import-service.php:32), [post writes](/Users/ahmadjalil/github/campusmanager/includes/class-event-import-service.php:67), [AJAX import](/Users/ahmadjalil/github/campusmanager/includes/class-event-importer.php:305).

The REST importer accepts any logged-in user with `edit_posts`, including roles without `publish_events` or permission to edit the matching event. It then defaults to `publish` and calls `wp_update_post` for duplicates without checking the target. The admin importer checks only `edit_events` and likewise updates a globally matched duplicate.

**Change:** distinguish create, publish, and update authorization; check the actual target with `current_user_can('edit_post', $id)`; enforce organization ownership for managers. Give trusted API-key imports an explicit, separate policy. Test contributors, managers from two organizations, editors, and API-key requests.

### 2. P1 — External-ID deduplication can redirect an authorized REST write to an unauthorized post

Evidence: [duplicate hook](/Users/ahmadjalil/github/campusmanager/includes/class-post-types.php:318).

`rest_pre_insert_event` looks up an arbitrary matching `external_id` and sets `$prepared_post->ID`. A manager allowed to create events, or update their own event, can thereby target another event without a new permission check. The lookup also does not join against posts to enforce post type. This is a distinct route from the custom importer.

**Change:** return a conflict for duplicates on create, or authorize the resolved target explicitly in a dedicated upsert endpoint. Never silently change the target of an update request. WordPress's [REST create implementation](https://developer.wordpress.org/reference/classes/wp_rest_posts_controller/create_item/) passes the prepared object to `wp_insert_post`, which is why assigning an ID here matters.

### 3. P1 — Manager restrictions are enforced in screens more consistently than in writes

Evidence: [organization registration](/Users/ahmadjalil/github/campusmanager/includes/class-post-types.php:84), [manager capabilities](/Users/ahmadjalil/github/campusmanager/includes/class-user-roles.php:177), [unassigned-event access](/Users/ahmadjalil/github/campusmanager/includes/class-user-roles.php:59), [event organization update](/Users/ahmadjalil/github/campusmanager/includes/class-rest-api.php:631), [meta-box save](/Users/ahmadjalil/github/campusmanager/includes/class-meta-boxes.php:647).

- Organizations have REST enabled and use the default creation capability. Managers have `edit_organizations` and `publish_organizations`, so hiding Add New does not prohibit REST creation. WordPress defaults `create_posts` to the post type's edit capability; see [capability generation](https://developer.wordpress.org/reference/functions/get_post_type_capabilities/).
- Managers may edit their assigned organization's title, slug, and status through REST; the field restriction helper is not a REST validation hook.
- Any event with an empty `organization_id` is editable by any assigned manager, even when another person authored it.
- The event REST field and meta-box save accept a submitted organization ID without forcing the manager's assigned organization.

**Change:** establish one write policy used by REST, imports, and forms. Explicitly deny organization creation for managers, reject restricted field changes before saving, limit unassigned draft access to the creator, and enforce event organization ownership on the server.

The legacy organization meta-box branch also calls `wp_update_post` from its own `save_post` callback without removing that callback. If invoked with an organization nonce, it can recurse; reading the “original” post after saving cannot restore its old title either. Replace that branch with validation before the write.

### 4. P1 — Cache keys mix organizations, date ranges, and pagination

Evidence: [cache key](/Users/ahmadjalil/github/campusmanager/assets/react/src/services/eventsApi.ts:218), [pagination merge](/Users/ahmadjalil/github/campusmanager/assets/react/src/hooks/useEvents.ts:208).

**Reproduced.** The key includes only year, month, category, and search. It excludes organization, page, page size, view, featured, and explicit start/end dates. Calling organization 10/page 1, organization 20/page 1, and organization 10/page 2 made one network request and returned the same response object three times. Organization blocks can appear empty after filtering another organization's cached events; load-more can append page one repeatedly.

**Change:** key by all normalized request parameters and API base URL; bypass or clear cache for an explicit refresh. Add a regression test covering different organizations, pages, and date ranges in one mounted session.

### 5. P1 — Replacing occurrences can destroy valid data before input is validated

Evidence: [series upsert](/Users/ahmadjalil/github/campusmanager/includes/class-event-import-service.php:252), [second occurrence writer](/Users/ahmadjalil/github/campusmanager/includes/class-event-series.php:349).

Existing occurrences are deleted before parsing every replacement datetime. An invalid later occurrence throws after the delete and possibly after earlier replacement inserts. The parent event and series have already changed, but the request returns an error. Database insert/update failures are also ignored. An explicitly empty occurrence array takes the opposite path: it returns early and leaves old occurrences intact.

**Change:** validate and normalize the complete payload first, define omitted versus empty-array behavior, then replace the series atomically with checked database results. Test malformed second occurrences, duplicate hashes, database failure, and intentional recurrence removal.

### 6. P1 — A beta tag would update the stable release manifest

Evidence: [tagged release and manifest publishing](/Users/ahmadjalil/github/campusmanager/.github/workflows/build-zip.yml:119), [default updater URL](/Users/ahmadjalil/github/campusmanager/unbc-events.php:43).

Every `v*` tag is published with `prerelease: false`, and every tag updates the manifest on `main`. Tagging the current `2.3.1-beta.1` candidate would therefore advertise it through the manifest used by stable installations. `makeLatest: false` does not prevent that manifest update.

**Change:** detect prerelease versions, mark them as prereleases, and prevent them from changing the stable manifest. Use a separate opt-in beta manifest. Scope workflow concurrency so an unrelated branch build cannot cancel a release.

## Correctness and data integrity

### 7. P2 — Day/week navigation and the upcoming list use a month-only dataset

Evidence: [date filters](/Users/ahmadjalil/github/campusmanager/assets/react/src/components/unbc-calendar.tsx:248), [day navigation](/Users/ahmadjalil/github/campusmanager/assets/react/src/components/calendar-views/day-view.tsx:33), [week state](/Users/ahmadjalil/github/campusmanager/assets/react/src/components/calendar-views/week-view.tsx:14), [load more](/Users/ahmadjalil/github/campusmanager/assets/react/src/components/unbc-calendar.tsx:446).

Requests always cover `calendarViewDate`'s month. Day and week components navigate their own local state without updating that request range. Crossing a month boundary displays missing events. List view also remains limited to the loaded month; its load-more button only increases the number of already-loaded items displayed. The 500-post limit can silently truncate busy months.

**Change:** keep the active date in the parent and fetch the visible range for each view, including leading/trailing calendar cells. Give upcoming lists real server pagination and load all required month pages. Test month boundaries and more than 500 matching posts.

### 8. P2 — List API requests do not actually enforce the upcoming-date cutoff

Evidence: [date query](/Users/ahmadjalil/github/campusmanager/includes/class-rest-api.php:148), [list strategy](/Users/ahmadjalil/github/campusmanager/includes/class-rest-api.php:752), [organization wrapper](/Users/ahmadjalil/github/campusmanager/assets/react/src/components/organization-events-wrapper.tsx:27).

List strategy supplies only `start_date`, but date filtering runs only when both bounds are present. Results are paginated in WordPress's default post-date order, not event-start order. Organization widgets then filter past events after retrieving just the first page. Fifty recent historical imports can crowd upcoming events out entirely.

**Change:** support independent date bounds and stable event-start ordering before pagination. Compute `hasMore` from page count/total instead of treating an exactly full final page as evidence of another page.

### 9. P2 — Occurrence dates, overnight events, and timezones lose information

Evidence: [occurrence expansion](/Users/ahmadjalil/github/campusmanager/includes/class-rest-api.php:243), [datetime transformation](/Users/ahmadjalil/github/campusmanager/includes/class-rest-api.php:428), [timezone handling](/Users/ahmadjalil/github/campusmanager/includes/class-rest-api.php:470), [admin import conversion](/Users/ahmadjalil/github/campusmanager/includes/class-event-importer.php:529).

Only series with more than one occurrence use occurrence datetimes; a single stored occurrence falls back to parent metadata. Expanded occurrences keep the start date and only the end time, so a 23:00–01:00 overnight occurrence becomes an end earlier than its start. The admin importer converts to the event's supplied timezone, while the API later interprets that local time in the site timezone. Cancelled-series status, all-day state, and occurrence overrides are not applied in the calendar projection.

**Change:** use a canonical start/end representation with a documented timezone policy. Preserve full occurrence start and end datetimes even for one occurrence, expose status/all-day metadata, and test overnight, multi-day, and DST cases.

### 10. P2 — Export/import is not a complete round trip

Evidence: [export record](/Users/ahmadjalil/github/campusmanager/includes/class-organization-import-export.php:434), [event import identity](/Users/ahmadjalil/github/campusmanager/includes/class-organization-import-export.php:682).

Exports include posts, metadata, taxonomy terms, and optional images, but not the custom series/occurrence tables. Restoring a recurring event therefore loses its schedule. Import deduplicates events only by title, so separate dates of “Weekly Meeting” can be discarded. Organization relations use titles, with raw old metadata IDs retained when no title resolves.

**Change:** version the export schema, include series/occurrences, and map source IDs to destination IDs for all relations. Deduplicate with stable external identifiers or a documented compound key. Validate by exporting and importing into a fresh test site and comparing the resulting event graph.

### 11. P2 — “Always create new” updates existing events

Evidence: [import execution](/Users/ahmadjalil/github/campusmanager/includes/class-event-importer.php:410), [post selection](/Users/ahmadjalil/github/campusmanager/includes/class-event-importer.php:508).

For `duplicate_handling=create`, execution still passes the found existing ID into `import_single_event`. That method updates the original, while the result counter reports a creation. This contradicts both the selected option and the preview.

**Change:** pass an existing ID only in update mode. Test all three modes against the same fixture and assert both post identity and counts.

### 12. P2 — Failed post writes can be reported as successful imports

Evidence: [REST import write result](/Users/ahmadjalil/github/campusmanager/includes/class-event-import-service.php:75), [admin import write result](/Users/ahmadjalil/github/campusmanager/includes/class-event-importer.php:510).

Both paths call post writes without enabling `WP_Error` returns, then check only `is_wp_error`. WordPress can return zero on failure; see the [documented return contract](https://developer.wordpress.org/reference/functions/wp_insert_post/). Processing then continues and can report success with post ID zero. Series counts likewise reflect submitted occurrences rather than successful inserts.

**Change:** request error objects, reject zero, check dependent writes, and report actual successful operations. Extend the current media-focused fixtures to include a failed parent save.

### 13. P2 — Managers' draft and trashed events disappear from their list

Evidence: [manager event query](/Users/ahmadjalil/github/campusmanager/includes/class-post-types.php:446).

The code first builds `post__in` using `get_posts` without a `post_status`, which selects published posts by default. That ID list then constrains the main admin query even when the manager selects Drafts or Trash.

**Change:** add the organization meta condition directly to the main query so WordPress can retain its selected status filter. Test publish, draft, pending, and trash views.

### 14. P2 — Block filters and category configuration do not match the frontend contract

Evidence: [ignored initial filters](/Users/ahmadjalil/github/campusmanager/assets/react/src/components/unbc-calendar.tsx:242), [expected config](/Users/ahmadjalil/github/campusmanager/assets/react/src/hooks/useCategoryConfig.ts:3), [actual config](/Users/ahmadjalil/github/campusmanager/includes/class-rest-organizations-controller.php:62).

The renderer passes configured initial category and organization filters, but the component always initializes both to `all`. Separately, `useCategoryConfig` expects `categoriesWithOrganizations`, `categoryRelationships`, and `autoAssignCategory`; the server returns a slug-to-name/variant map. That suppresses configured organization-dropdown behavior. Related-category filtering is also applied after a stricter single-category server query, so it cannot recover omitted events.

**Change:** initialize from props and give configuration a single typed, versioned contract. Keep color data and relationship settings explicit. Test configured blocks, not only the default calendar.

### 15. P2 — Server cache invalidation bypasses persistent object caches

Evidence: [cache clearing](/Users/ahmadjalil/github/campusmanager/includes/class-rest-api.php:687), [category cache clearing](/Users/ahmadjalil/github/campusmanager/includes/class-category-colors.php:254).

Invalidation directly deletes rows from `wp_options`. With an external object cache, WordPress stores transients through `wp_cache_set`; those cached responses survive this SQL deletion. See [WordPress transient storage](https://developer.wordpress.org/reference/functions/set_transient/). Organization-name changes also affect rendered event metadata but are not an invalidation trigger.

**Change:** include a cache-generation value in keys and bump it after completed relevant writes, or track keys and delete through the transient API. Test with and without Redis/object caching.

### 16. P2 — Late network responses can overwrite newer filters

Evidence: [fetch effect](/Users/ahmadjalil/github/campusmanager/assets/react/src/hooks/useEvents.ts:139), [load-more operation](/Users/ahmadjalil/github/campusmanager/assets/react/src/hooks/useEvents.ts:208).

There is no abort signal or request-generation guard. A slower old month/category request can replace a newer result. An old load-more request can append records after filters change. Error paths also leave old pagination state in place.

**Change:** cancel superseded requests or ignore stale completions, reset pagination when query identity changes, and merge pages by event identity. Verify with deliberately reversed response order.

### 17. P2 — Calendar exports do not escape iCalendar text

Evidence: [ICS generation](/Users/ahmadjalil/github/campusmanager/assets/react/src/components/event-dialog.tsx:68).

Titles, descriptions, locations, and organizer names are interpolated directly into content lines. Multiline descriptions already produced by the backend become literal new lines instead of an escaped value, causing truncated descriptions or unintended calendar properties. Line endings and folding are also handled manually.

**Change:** use a tested iCalendar serializer, preserve proper UTC/date-only semantics, and test multiline descriptions, commas, semicolons, backslashes, and long Unicode text. Also carry cancelled/all-day state from the canonical event model.

## Usability, performance, and maintenance

### 18. P2 — Important calendar actions are inaccessible from the keyboard

Evidence: [month event cards](/Users/ahmadjalil/github/campusmanager/assets/react/src/components/calendar-views/month-view.tsx:184), [day navigation](/Users/ahmadjalil/github/campusmanager/assets/react/src/components/calendar-views/day-view.tsx:80), [organization event cards](/Users/ahmadjalil/github/campusmanager/assets/react/src/components/organization-events-list.tsx:150).

Several event cards are clickable `div` elements without focusability or keyboard activation. Icon-only day/week navigation buttons lack accessible names. This assessment is from markup; a browser/screen-reader audit remains necessary.

**Change:** use native buttons/links, label navigation, preserve visible focus, and announce loading/errors. Verify the full flow using Tab, Enter/Space, Escape, and focus restoration after closing event details.

### 19. P2 — Both React applications and styles load on every frontend page

Evidence: [global enqueue](/Users/ahmadjalil/github/campusmanager/includes/class-calendar-blocks.php:119), [unused content check](/Users/ahmadjalil/github/campusmanager/includes/class-calendar-blocks.php:138), [bundle setup](/Users/ahmadjalil/github/campusmanager/assets/react/vite.config.js:23).

The plugin enqueues both calendar and widget bundles and both stylesheets whether or not the page contains either component. Current committed assets total 769,102 bytes uncompressed, or approximately 230 KB gzip, before other page assets. Each app bundles React separately, and the two CSS files have the same byte size. Theme detection also writes a global `html.dark` class, which can interfere with the host site's theme choice.

**Change:** enqueue the needed bundle from actual block/shortcode rendering, account for template/widget usage, share runtime/style code where practical, and scope theme behavior to the component. Measure on a page without campus widgets and a page containing both.

### 20. P2 — Public API work is unbounded and repeats database queries

Evidence: [request arguments](/Users/ahmadjalil/github/campusmanager/includes/class-rest-api.php:25), [range lookup](/Users/ahmadjalil/github/campusmanager/includes/class-rest-api.php:148), [per-event occurrence lookup](/Users/ahmadjalil/github/campusmanager/includes/class-rest-api.php:800).

`per_page` is sanitized but has no maximum when both dates are supplied. The API first loads every matching regular-event ID, applies `DATE()` to the indexed occurrence column, then looks up series and occurrences separately for each returned post. Large ranges and many recurring events increase memory, response size, and query count.

**Change:** validate bounded page sizes/ranges, use datetime range comparisons, batch-load occurrences for the selected posts, and paginate a stable event/occurrence projection. Benchmark with realistic annual volume and a large recurrence set before changing storage design.

### 21. P2 — Packaging is not gated on a reproducible, checked build

Evidence: [release workflow](/Users/ahmadjalil/github/campusmanager/.github/workflows/build-zip.yml:1), [scripts](/Users/ahmadjalil/github/campusmanager/assets/react/package.json:6), [distribution exclusions](/Users/ahmadjalil/github/campusmanager/.distignore:1).

CI packages committed build artifacts without rebuilding frontend code, linting PHP, or executing tests. `build:all` builds only the calendar editor block, omitting the events-list, today-widget, and organization-field editor packages. ESLint has no configuration; there is no TypeScript type-check script/config. `.distignore` does not exclude `node_modules`, so a developer's local packaging process can include dependency trees unless an extra exclusion is supplied.

**Change:** pin Node/npm/PHP versions; install and build all five frontend packages; add TS-aware lint/type checks and PHP lint/regression checks; inspect ZIP contents before release. Keep the already-added media tests and add authorization, occurrence, export round-trip, and cache regressions first.

## Further improvements after the correctness work

- **Dependency cleanup:** the audit flags `react-router-dom`/`react-router`, `wpapi`/`parse-link-header`, `form-data`, and `qs`. `react-router-dom` has no source imports in this project; `wpapi` appears in a legacy API module. Remove unused dependencies, then update what is actually shipped. Do not treat audit metadata as proof of a remotely exploitable WordPress flaw. Raw audit output is saved at `/tmp/campusmanager-review.cuigot/audit.json` for this session.
- **One event service and schema:** REST import, admin import, export import, meta boxes, and series management each implement overlapping event writes. Consolidating validation, deduplication, ownership checks, and time conversion would prevent fixes from reaching only one path.
- **Correct REST URL use:** organization/category hooks hardcode `/wp-json/...`, while localized URLs already exist. Use those URLs to support WordPress in a subdirectory and alternative REST routing. Paginate organization/category lists beyond their first 100 entries.
- **Error and empty-state clarity:** organization fetching catches errors and returns an empty list, hiding failures. Calendar search reads `metadata.description`, while descriptions live on the event object. Show useful retry states and search the actual description field.
- **Remove misleading placeholders:** `create-calendar-event` returns success and an example Google URL without creating anything. Disable it or return an explicit unsupported response until implemented.
- **Guard diagnostic logging:** calendar/block lifecycle messages are logged on normal requests. Restrict routine messages to debug mode.
- **Avoid unrelated writes during page requests:** organization template initialization scans unassigned `wp_template` posts and assigns them to the current theme. Make repair an explicit scoped migration/admin operation rather than changing arbitrary templates during normal initialization.
- **Refresh documentation:** the README still names the event post type `unbc_event`, documents `/wp/v2/organizations` rather than the registered singular REST base, has conflicting WordPress requirements, and presents 2.1.0 as latest. Preserve the useful beta/media notes while documenting the actual build and test process.

## Suggested implementation order

1. Close write-policy gaps and separate beta releases from stable updates (findings 1–3 and 6).
2. Fix cache identity, visible date ranges, and upcoming-event querying (4, 7, 8, 14–16).
3. Make imports transactional and exports lossless; normalize occurrence dates (5, 9–13, 17).
4. Add build/test gates, keyboard support, conditional asset loading, and query bounds (18–21).

For each group, add targeted regressions for the actual failing behavior before refactoring the shared architecture. The current media-warning work already provides a useful pattern for distinguishing a saved event from a partially failed import.
